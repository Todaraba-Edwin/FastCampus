## 8. LLM의 비용 문제와 SLM

### (1) LLM의 비용 문제와 SLM

- GPT-4, Claude 등 대규모 언어모델의 API 비용 급증
- 학습/추론 단계의 높은 컴퓨팅 자원 요구
- 엣지·모바일 환경에 배포 불가능
- **SLM(Small Language Model)의 등장**: 저비용·고효율 대안

### (2) LLM 대체: 경량 모델(SLM)의 부상

- 1B~13B 규모의 소형 모델로도 충분한 성능 달성
- 로컬 실행 가능 → 데이터 프라이버시 보장
- 추론 속도 향상, 응답 지연 시간 단축
- 모바일·IoT 디바이스 통합 가능
- 엔터프라이즈 환경에서 비용 절감 (API 호출 vs 로컬 운영)

### (3) Large Language Model의 한계와 Small Language Model

| 측면 | LLM | SLM |
|------|-----|-----|
| 모델 크기 | 70B~405B+ | 1B~13B |
| 성능 | 최고 수준 | 특정 작업 최적화 |
| 배포 | 클라우드 의존 | 로컬·엣지 가능 |
| 비용 | 높음 (API) | 낮음 (로컬) |
| 지연 시간 | 상대적 높음 | 극단적 단축 |

### (4) Llama

Meta 개발 오픈소스 언어모델 계열 (버전별 진화)

- **Llama 1** (2023년 2월)
  - 초기 공개, 7B~65B 모델 제공
  
- **Llama 2** (2023년 7월)
  - 상용화 허용, 대폭 성능 개선
  
- **Llama 3** (2024년 4월)
  - 8B, 70B 모델, 컨텍스트 길이 8K
  - 주요 벤치마크에서 GPT-4 경쟁 수준 성능
  
- **Llama 3.1** (2024년 7월)
  - 405B 초대형 모델 추가
  - 멀티링구얼 지원, 코딩·추론 능력 강화
  
- **Llama 3.2** (2024년 9월)
  - 1B, 3B 초경량 모델로 SLM 진입
  - 멀티모달 비전 능력 추가 (11B, 90B)
  - 엣지·모바일 디바이스 배포 가능

### (5) MOE(Mixture of Experts) 아키텍처

SLM과 LLM의 장점을 결합한 효율적 아키텍처

**핵심 메커니즘**
- 여러 전문화된 Expert 네트워크 + Router(게이팅 함수)
- 각 입력 토큰에 대해 필요한 Expert만 선택적 활성화
- 전체 Expert 중 소수 subset만 연산 수행

**파라미터 vs 연산 효율**
- 총 파라미터: 크다 (모든 Expert의 합)
- 활성화 파라미터: 작다 (선택된 Expert만)
- 실제 연산량: LLM 대비 훨씬 적음
- **결과**: LLM 수준의 성능 + SLM 수준의 효율성

**Meta의 선택: MOE 회피**
- Llama 3.1 405B: 표준 Transformer 아키텍처 도입 (MOE 미적용)
- 이유: 훈련 안정성 극대화, 복잡도 감소
- 405B 모델도 단순 스케일링으로 충분한 성능 달성

**다른 회사의 MOE 추진**
- Mistral: Mixtral 8x7B로 효율성 강조 (8개 Expert, 각 7B)
- Google: Gemini-1.5에서 MOE 구조 채택
- xAI: Grok-1에서 MOE 활용
- DeepSeek: DeepSeek-V3에서 MOE 고도화

**핵심**: 같은 성능 목표도 아키텍처 선택이 다름 (안정성 vs 효율성)

### (6) DeepSeek의 등장과 SLM의 재평가

**DeepSeek-V3 (2024년 12월)**
- 671B 파라미터 MOE 모델
- 학습 비용 $5.6M (vs GPT-4: $50-100M)
- 효율적 스케일링의 새로운 기준 제시

**DeepSeek-R1 (2025년 1월)**
- 추론 능력 강화 버전
- **Distillation 기술**: 대규모 모델의 능력을 작은 모델에 전수
- 14B 모델이 기존 32B Qwen 능가
- 7B-70B 모델 범위에서 o1-mini 수준 성능

**알리바바 Qwen의 도전**
- Qwen2.5: Meta Llama 3.1 성능 초과
- 글로벌 오픈소스 다운로드 50% 이상 점유
- 4B~72B 범위 SLM도 경쟁력 있는 성능 제공

**SLM의 "멸망" 아닌 "재평가"**
- 기존 선입견: SLM = 저성능 대체품
- 새로운 현실: Distillation으로 작은 모델도 고성능 가능
- 로컬 실행 가능한 고성능 모델의 시대 도래
- 프라이버시·비용 효율성의 우위 부각

**Llama의 위치 변화**
- Meta 독점 생태계 종료
- Qwen, DeepSeek의 경쟁으로 차별화 압박
- 성능과 효율성의 새로운 경쟁 기준 형성

### (7) AI 에이전트의 추론능력 비약적 향상

**DeepSeek R1의 추론 혁신 (2025년 1월)**
- 투명한 추론 경로 공개 (Extended Thinking)
- AIME 2025: 정확도 70% → 87.5% 상향
- 평균 23,000 토큰으로 깊이 있는 추론 수행
- 오픈소스 + 자체 호스팅 가능

**Google Gemini 2.5 Pro의 대응**
- Deep Think Mode: 병렬 가설 검증 후 응답
- AIME 점수: 92.0%, LiveCodeBench: 77.1%
- 1,000,000 토큰 컨텍스트 윈도우 (업계 최대)
- 장문서 분석 + 추론 동시 수행

**Anthropic Claude의 강화 (2025년 5월)**
- Claude Opus 4: 200K 컨텍스트, 최고 성능
- Extended Thinking: 추론 과정 시각화
- Claude Sonnet 4: 고성능 + 비용 효율성

**비용-성능 역전 현상**
- DeepSeek R1: o3 대비 4배 저렴, 유사 추론 품질
- 오픈소스 모델의 수렴 현상
- 상용 모델도 "비용 효율성" 강화 필요

**AI 에이전트의 변화**
- 단순 생성에서 깊이 있는 추론으로 전환
- 추론 토큰 증가 = 복잡 문제 해결력 향상
- 에이전트 신뢰도·정확성 대폭 상승

**기술적 혁신: 강화학습(RL) vs 파인튜닝(SFT)**

*기존 방식*
- Supervised Fine-Tuning (SFT): 기존 데이터 패턴 모방
- 제한: 새로운 추론 능력 습득 어려움

*새로운 방식*
- Reinforcement Learning (RL): 탐색 + 피드백을 통한 학습
- DeepSeek-R1-Zero: 순수 RL (SFT 없이 추론 능력 창발)
- DeepSeek-R1: 하이브리드 접근
  - Cold-start: 소규모 Chain-of-Thought 데이터로 SFT
  - RL fine-tuning: 반복적 강화학습으로 추론 강화
  - 결과: 일관성 + 추론 능력 동시 확보

*기술적 의의*
- 추론은 강화학습으로만 가능 (SFT로는 한계)
- Test-time compute: 추론 단계에서 계산량 증가
- Google, Anthropic도 유사 방식 채택 (Deep Think, Extended Thinking)

### (8) Llama 4와 Meta의 위기: 오픈소스 vs 수익화의 딜레마

**Llama 4 출시의 배경**
- DeepSeek의 성공으로 경쟁 심화
- 2025년 4월 Llama 4 출시 (Scout, Maverick 모델)
- Behemoth 모델은 여전히 학습 중
- Scout: 17B 활성 파라미터, GPT-4o·Gemini 2.0 경쟁

**경영진의 이상과 현실의 충돌**

*Zuckerberg의 오픈소스 신앙*
- "초지능(AGI)의 이점을 전 세계에 공유해야 한다"
- 오픈소스 = 중앙화 방지 + 민주화
- 오픈소스 정책으로 전략적 우위 확보

*현실의 재정 압박*
- 2025년 AI 인프라 투자: $72.2B
- 2026년 예상: $115-135B (거의 2배)
- 이윤율 급락: 48% → 41% (1년)
- 향후 감가상각비 추가 압박 예상

**전략적 전환: 폐쇄형 모델로의 방향 전환**

*내부 실패와 외부 압박*
- Llama 4 내부 실패 (성능 기대 미달?)
- 투자자 압박: "언제 수익화할 것인가?"
- 경쟁사 (OpenAI, Google) 상용화 성공 목격

*새로운 접근*
- Muse Spark (2026년 4월): 첫 폐쇄형 모델
- Avocado 모델 (Q1 2026): 상용화 목표
- "개방"에서 "통제"로 전략 재설정
- 직접 수익화: 사용자 API 구독 모델

**AI 생태계에서의 위치 변화**

*오픈소스 리더에서 상용 경쟁자로*
- Llama: 경쟁 무기 (직접 수익화 X)
- Muse/Avocado: 경쟁 상품 (직접 수익화 O)
- OpenAI, Google과의 동일선상 경쟁
- Qwen, DeepSeek과의 비용 경쟁 심화

*비즈니스 모델의 근본적 전환*
- 광고 + AI (내부용) → AI 직접 판매
- 오픈소스로 진입장벽 낮추는 전략 종료
- 프리미엄 폐쇄형 모델로 고수익 추구

**Meta의 고민과 미래**
- 이상(오픈소스 민주화) vs 현실(수익 압박) 모순
- 대규모 자본 투자의 정당성 입증 필요
- AI 생태계 주도권 유지 vs 경제성 확보의 균형

### (10) 한국의 독자 AI: 소버린 파운데이션 모델

**소버린 AI(Sovereign AI)의 의미**
- 독자 개발·운영으로 외부 API 의존 최소화
- 데이터 보안·AI 주권 확보 (국가 전략)
- 한국어·한국 문화 특화 학습 데이터

**정부 지원 한국형 파운데이션 모델 프로젝트**
- 5개 정예팀 선정 (LG, 업스테이지, 네이버, SKT, NC)
- 글로벌 AI 강국(미국 43개, 중국 30개) 대비 한국 8개 모델
- 미국·중국 다음 세계 3위 AI 개발 국가로 진입

**K-엑사원(EXAONE) - LG AI연구원**
- 236B 규모 프런티어 모델, 글로벌 7위 달성
- 26만 토큰 초장문맥 (A4 400장 이상 한번에 처리)

**K-엑사원 2.0의 혁신**
- 750B 파라미터 (기존 대비 3배 증가)
- 메모리·연산량 70% 절감 + 추론 속도 150% 향상
- 하이브리드 어텐션 기술로 효율성·성능 동시 달성

**솔라(Solar) - 업스테이지**
- 100B 파라미터 한국어 특화 모델
- 슬라이드 생성·심층 리포트·팩트체크·에이전트 검색 등 고난도 작업 수행

**솔라의 차별성**
- 장애 자동 감지·대체 시스템 (안정성 강화)
- GPU 효율 극대화 학습 커널 최적화

**HyperCLOVA X - 네이버**
- 네이버 생태계(검색·콘텐츠·쇼핑) 전역 적용
- 한국어 이해·서비스 통합 최적화

**한국형 AI의 차별점**

### (12) 토크나이저에서 한글의 불리성: 비영어권의 숨은 비용

**토크나이저 문제의 본질**
- LLM이 텍스트를 처리하기 위해 작은 단위(토큰)로 분해
- BPE 알고리즘: 바이트 단위 처리 → 한글 1글자 = 3바이트
- 훈련 데이터 99%가 영어 → 영어 최적화, 한글 부족

**토큰 효율의 격차**
- 영어 "Hello world" = 2토큰
- 한글 "안녕하세요" = 4-5토큰
- 동일 의미 비용: 한글이 3-5배 비쌈
- 같은 $20 구독료로 한국어는 영어의 1/3 사용량만 가능

**고유명사의 심각성**
- "Seoul" (1-2토큰) vs "서울" (2-3토큰)
- "Python" (1토큰) vs "파이썬" (3토큰)
- "Kim Hae-soo" (3토큰) vs "김해수" (4토큰)
- 한국 지명·인명: 토크나이저가 인식 불가 → 바이트 분해

**한글의 구조적 복잡성: 분절(자모) 문제**
- 영어: 26자 알파벳 + 조합 규칙 → 비교적 단순하고 규칙성 있음
- 한글: 초성(19) × 중성(21) × 종성(28) = 수만 개 조합 → 규칙성 부족
- 한글은 "자모 조합"으로 무한히 새로운 글자 생성 가능 → 예측 불가능
- 토크나이저 입장: 한글 글자는 "본 적 없는 새로운 조합"일 가능성 높음
- 결과: BPE 학습 시 한글은 자모 단위로 분해될 수밖에 없음

**구조적 불공정성**
- 영어 우월성: "the", "ing", "tion"은 자동으로 1토큰
- 한글 차별: 글자 조합 부족 → 글자 단위 분해
- 결과: "같은 돈, 다른 서비스" (영어권 vs 한국)

**해결책의 부재**
- 구글 GLM은 중국어 데이터로 해결했으나
- Claude, GPT는 한글 데이터 추가 없음
- Sovereign AI 필요성 재확인

### (13) LLM에서 Agent로: 자율 지능의 등장

**Agent의 정의**
- LLM이 Tool use, Planning, Reasoning을 통해 자율적으로 행동·의사결정하는 시스템
- 단순 텍스트 생성 → 문제 해결 능력 획득

**진화 단계**

*Phase 1: Tool Learning (2023)*
- Toolformer: LLM이 자동으로 API 호출 학습
- Gorilla: 문법 규칙에 맞는 API 호출

*Phase 2: Executable Environment (2024)*
- CodeAct: Python 코드 실행으로 즉시 피드백
- MCP(Model Context Protocol): 에이전트-도구 표준화

*Phase 3: Reasoning + Execution (2025)*
- o1·Gemini 4 Argon: 추론 모델 대두
- Multi-agent systems: 여러 에이전트 협력
- 네이티브 Tool-use 내장

**현재의 Agent 능력**
- 자율 계획: 목표 달성 경로 자동 수립
- 다중 도구: 코드·API·검색·DB 동시 활용
- 피드백 루프: 실행 결과 → 재계획
- 에이전트 Swarm: 수백 개 서브에이전트 조율

**미래 (2026+)**
- 다중 에이전트 조직: AI 팀이 독립적으로 업무 수행
- 자율 소프트웨어 개발: 코드 작성부터 배포까지
- 지속 학습: 작업 경험으로 자동 개선

**사례: 과거 에이전트 vs 현재 AI 에이전트**

*과거: 로봇청소기 (Autonomous but Limited)*
- 기능: 정해진 청소 경로만 반복 실행
- 인식: 센서로 장애물·벽 감지만 가능
- 상호작용: 앱에서 "시작" "중지" 명령만 가능
- 학습: 없음 (같은 로직 반복)

*현재: Meta Muse·OpenAI Dots*
- 기능: 이메일 작성→조사→계획 수립→실행 자동 완성
- 인식: 자연어로 목표 이해 후 최적 경로 자율 계획
- 상호작용: 대화로 추가 지시·승인 요청 → 협력형
- 학습: 매 작업마다 추론 과정 최적화

*핵심 차이*
- 로봇청소기: "정해진 것만 한다" (Programmed)
- AI 에이전트: "목표를 말하면 최적 방법을 찾는다" (Reasoned)
- 진화: 고정 알고리즘 → 언어 이해 → 자율 추론

### (14) AI 코딩 에이전트의 진화: Codex → Cursor → Claude Code

**Codex (OpenAI, 2021년 8월)**

GPT-3를 GitHub 54만 개 리포지토리 159GB 코드로 파인튜닝한 모델. 2021년 8월 API 공개(비공개 베타)로 "자연어 → 코드 변환" 혁신 시작. GitHub Copilot의 기반이 되어 VSCode 자동완성으로 개발자 생산성 향상. 2023년 3월 GPT-4 전환으로 Codex API 중단되며, 초기 AI 코딩 에이전트 시대 종료. **의의**: "AI가 코드를 생성할 수 있다" 증명 (LLM의 코드 분야 능력 확인)

**Cursor (Anysphere, 2023년 3월)**

VSCode를 포크해 AI를 네이티브 통합한 IDE. 2023년 3월 v0.1 출시로 Codex 이후 대체재 등장. 2023년 9월 OpenAI Startup Fund에서 $800만 투자로 본격 성장. 2025년 10월 Cursor v2.0 출시 시 자체 LLM 'Composer 1' 포함, 종속성 탈피. 2026년 4월 Cursor 3.1 현재. **의의**: "독립형 AI IDE의 가능성" 증명 (코드 완성 → 코드 생성 → 다중 라인 리라이트)

**진화 흐름**
- Codex (2021): 기반 마련 (자연어→코드)
- Cursor (2023): 독립형 에디터 (사용자 중심)

### (15) Agent 시대의 패러다임 전환: Prompt Engineering → Context Engineering

**Prompt Engineering (이전 패러다임)**

정의: "어떻게 물을 것인가" - 마법사의 주문처럼 한 번의 명령으로 원하는 답 도출

특징
- 단일 텍스트 명령어 최적화
- "좋은 프롬프트" 작성에 집중
- 일회성 상호작용 중심

한계
- Agent의 복합 작업 해결 불가
- 맥락 손실 (컨텍스트 윈도우 제한)
- 메모리·도구·문서 통합 부족

**Context Engineering (새로운 패러다임)**

정의: "무엇을 포함시킬 것인가" - Agent가 작동하는 전체 정보 환경 설계

특징
- 메모리·문서·도구·대화 이력 통합
- 동적·반복적 컨텍스트 구성
- Signal-to-noise ratio 최적화
- 실시간 맥락 조정

범위: 단일 명령 → 전체 추론 파이프라인

**핵심 통찰**
- "Agent 실패의 80%는 모델 실패가 아닌 컨텍스트 실패"
- 올바른 정보, 올바른 형식, 올바른 시점 제공이 핵심

**요구되는 역량 (Context Engineering)**

1. **정보 구조화**: 메모리(단기/장기), 문서, 도구를 계층적으로 정리
2. **맥락 설계**: 에이전트가 이해할 수 있는 정보 환경 구축
3. **우선순위 결정**: 컨텍스트 윈도우 내 최고 신호 정보 선택
4. **동적 조정**: 에이전트 추론 과정에 따라 실시간 컨텍스트 수정
5. **시스템 설계**: 메모리→검색→도구→응답 파이프라인 통합
6. **에이전트 사고 이해**: Agent의 추론 패턴을 예측해 필요 정보 선제적 제공

**실전 예시: Claude Code의 Context Engineering**

기존 Prompt: "이 버그를 고쳐줘"

Context Engineering:
- 프로젝트 아키텍처 (Auto Memory)
- 관련 코드 파일 (자동 검색)
- 버그 재현 단계 (도구: 터미널)
- 유사 버그 이전 해결책 (메모리)
- 팀 코딩 규칙 (컨텍스트)
- 현재 브랜치·PR 상태 (Git 통합)

→ Agent가 "완전한 정보"를 갖추고 자율 해결

**Prompt vs Context Engineering 비교**

| 구분 | Prompt Engineering | Context Engineering |
|------|-------------------|-------------------|
| 초점 | 어떻게 묻을까 | 무엇을 포함할까 |
| 범위 | 단일 텍스트 | 전체 정보 환경 |
| 최적화 | 명령 표현 | Signal-to-noise |
| 상호작용 | 일회성 | 반복·동적 |
| 실패 원인 | 나쁜 지시 | 부족한 맥락 |

**미래 개발자의 핵심 역량**
- Prompt 작성 < Context 설계
- "좋은 프롬프트" < "좋은 컨텍스트"
- 명령 최적화 < 정보 아키텍처 설계

### (16) AI 혁명의 대장정: Word2Vec (2013) → Opus 4.6 / GPT-6 Astra (2026)

**AI 역사의 5단계 진화 (2013-2026, 13년)**

**Stage 1: 임베딩의 시작 (2013)**
- **Word2Vec** (Google, Tomas Mikolov)
- 개념: 단어를 "벡터(숫자 리스트)"로 변환
- 혁신: "의미 있는 단어 표현" 가능
- 한계: 개별 단어만 처리, 문맥 무시

**Stage 2: 아키텍처 혁명 (2017)**
- **Transformer** (Google, Ashish Vaswani)
- 개념: RNN 제거, Self-Attention 중심
- 혁신: 병렬 처리 → 대규모 학습 가능
- 의의: 현대 LLM의 기초 아키텍처

**Stage 3: 자동 회귀 대형 모델 (2018-2020)**
- **GPT (2018)** → **GPT-2 (2019)** → **GPT-3 (2020)**
- 개념: Transformer 기반 자동 회귀 생성
- 진화: 70M → 1.5B → 175B 파라미터
- 의의: "생성형 AI"의 실현

**Stage 4: 대중화와 경쟁 (2022-2024)**

*2022년 11월: ChatGPT*
- 100만 사용자 2개월 달성 (역사상 최단)
- AI의 대중화 시작

*2024년*
- Claude Opus, GPT-4 Turbo, Gemini 등 경쟁 심화
- 각사 고유 기술 개발 (MCP, Tool use 표준화)
- 에이전트 프로토타입 등장

**Stage 5: 에이전트 시대의 정점 (2025-2026)**

*2026년 2월: Claude Opus 4.6 (Anthropic)*
- **기능**: 1M 토큰 컨텍스트, Agent Teams, Adaptive Thinking
- **성능**: 장문서 검색 18.5% → 76% 향상
- **특징**: 다중 에이전트 병렬 처리, 자동 추론 깊이 선택
- **용도**: 엔터프라이즈 코딩, 보안 분석, 에이전트 조율

*2026년 9월: GPT-6 Astra (OpenAI)*
- **출시**: 2026년 9월 4일
- **평가**: "생성 모델의 한 세대 도약"
- **강점**: 사이버보안, 전문 업무, 소프트웨어 엔지니어링, 과학 분야
- **특징**: Reasoning + Execution 통합

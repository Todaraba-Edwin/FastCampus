## 첫째, Naive RAG의 문제점

### (1) 사용자 질문 구체화

**등장이유**
- 원본 질문이 모호하면 검색 결과 부정확
- 질문 확장/구체화로 검색 정확도 개선

**내용**
- Query Expansion: 동의어/관련어 추가로 검색 범위 확대
- Query Refinement: 질문을 더 명확하고 구체화된 형태로 재작성
- Pseudo-Relevance Feedback: 초기 검색 결과로 질문 개선 후 재검색
- Query Decomposition: 복합 질문을 여러 단순 질문으로 분해

### (2) 문서파싱

#### 등장이유

- Naive RAG의 한계
  - 문서에서 단순히 텍스트만 추출 → 표, 이미지, 레이아웃 정보 손실
  - 기존 OCR/NLP 파이프라인은 단어, 문단, 표 간의 관계 이해 불가능
  
- 해결의 필요성
  - 비정형/반정형 문서의 가변성을 체계적으로 처리
  - LLM 기반 파싱으로 텍스트, 이미지, 구조를 동시에 이해

#### 내용

- **정의**: PDF, Word, HWP 등 다양한 문서 형식에서 텍스트, 표, 이미지, 계층적 구조를 추출하여 AI가 활용할 수 있는 구조화된 데이터(JSON, HTML, Markdown)로 변환하는 전처리 기술

- **DLA (Document Layout Analysis)**
  - 페이지 레이아웃 구조 분석
  - 텍스트, 표, 이미지의 공간적 위치 파악
  
- **TSR (Table Structure Recognition)**
  - 표의 행/열 구조 자동 인식
  - 복잡한 다층 테이블도 정확히 인식
  
- **LLM 기반 OCR**
  - 다양한 문서 유형에서 콘텐츠 정확하게 추출
  - 광학 문자 인식(OCR) + 의미론적 이해 결합
  
- **노드 기반 추출 및 메타데이터 생성**
  - 서로 다른 정보 유형 간의 관계 생성
  - 청킹에 최적화된 구조화된 데이터 생성
  - 문맥 인식 메타데이터로 검색 정확도 향상

### (3) 구조적 청킹

#### 등장이유

- Naive RAG의 한계
  - 고정된 토큰 길이로 단순 분할하면 문서의 논리적 단위 무시
  - 의미 있는 경계를 파괴하여 문맥 손상 및 정보 단절 발생
  
- 해결의 필요성
  - 문서의 계층적 구조(헤더, 섹션, 문단) 보존하며 분할
  - 검색 정확도 및 LLM 추론 정확도 20~30% 향상

#### 내용

- **정의**: 임의의 토큰 길이 제한이 아닌 문서의 원래 논리적 구조(H1, H2, H3, 문단, 리스트, 표)를 기반으로 의미 있는 단위로 분할하는 방식

- **계층적 청킹 (Hierarchical Chunking)**
  - 문서의 목차 구조(제목 레벨) 인식하여 섹션 단위로 분할
  - 상위 헤더 아래의 모든 콘텐츠를 논리적으로 묶음
  
- **마크다운 기반 청킹 (Markdown-Based Chunking)**
  - PDF를 마크다운으로 변환 (###, **, |---|등의 구조화 태그 생성)
  - LLM이 단순 줄글보다 구조화된 형식 처리 시 추론 정확도 향상
  
- **DOM 기반 청킹**
  - HTML/XML의 DOM 구조에 따라 요소별로 분할
  - 웹 문서의 의미 있는 블록 단위 보존
  
- **스마트 청킹 (Smart Chunking)**
  - 청크 경계의 문맥을 고려한 동적 분할
  - 각 청크가 독립적으로 의미를 가질 수 있도록 최적화

### (4) 리랭킹

#### 등장이유

- Naive RAG의 한계
  - 벡터 검색만으로는 관련 문서를 놓치거나 무관련 문서 포함 (낮은 재현율, 낮은 정밀도)
  - "Lost in the Middle" 현상: 관련 정보가 무관련 결과에 묻혀 순서가 뒤로 밀림
  
- 해결의 필요성
  - 빠른 검색(재현율 확보) + 정밀한 재평가(정밀도 향상) 이단계 방식
  - 24~48% 성능 향상 (TREC 데이터셋 기준)

#### 내용

- **정의**: 초기 검색으로 반환된 후보 청크들(보통 20~100개)을 두 번째 모델로 재평가하여 관련성 순서를 조정하는 기법

- **이단계 검색 파이프라인 (Two-Stage Retrieval)**
  - 1단계(Bi-encoder): 빠른 벡터 검색으로 광범위한 후보 추출
  - 2단계(Cross-encoder): 각 후보를 쿼리와 함께 입력하여 정밀하게 재평가
  - 토큰 수준의 상호작용으로 의미 관계 정확히 포착
  
- **Cross-Encoder 기반 리랭킹**
  - 쿼리-문서 쌍을 함께 처리하여 모든 상호작용 고려
  - Bi-encoder(임베딩 기반)보다 의미 이해도 높음
  - 속도는 느리지만 정확도 우월
  
- **Bi-Encoder vs Cross-Encoder 역할 분담**
  - **Bi-Encoder (초기 검색)**: 매우 빠름, 병렬 처리 가능, 저비용
  - **Cross-Encoder (리랭킹)**: 느리지만 높은 정확도, 상위 N개에만 적용
  
- **실전 패턴**
  - 빠른 Bi-encoder로 상위 N개를 먼저 추린 후, Cross-encoder로 정밀하게 리랭킹
  - 최고의 성능과 효율성 조합 실현
